# 预注册：v2b（D 组 = 改进信息输入的 LLM Judge）

写于 2026-10-20，此时 v2 网格（A/B/C）仍在运行。D 组和留出任务都还没有任何真实 LLM 运行结果。

## 背景与动机（已经看到的现象）

v2 中 stagnant_search 的 3 个种子里，B 组（LLM Judge，提示词 v1）共提出 7 次提议，**全部选择 objective**。它的理由都正确识别出"多样性丧失、种群聚集"，却都归因到目标权重。优化器参数虽然列在输入里（`mutation_sigma` 卡在下限 0.005、`crossover_rate` 为 0），但从没被选中过。原版 Analyzer 的提示词规定只给出目标层面的建议，报告里写着 "Strategic Recommendations (objective-level only)"。

**假设**：Judge 获得的证据被 Analyzer 框定在了目标层面。如果给 Judge 一份独立于 Analyzer 的运行诊断，并要求它逐一评估五类目标，它会在问题位于目标层以外时选择正确的干预目标。

## D 组的改动（只在 Judge 一侧，不改 A、B、C 的执行路径）

- **提示词 v2**：
  - 说明 Analyzer 按设计只提目标层面的建议，因此它的报告不能作为"问题在目标层"的证据；
  - 要求先给出 `target_assessment`，对五类目标各写一句评估，再做选择。
- **诊断信息**（由 controller 直接计算，所有 SAGA 运行都能得到）：
  - 各目标分数的统计，以及超出声明范围的数量；
  - 各目标在历次迭代中的最佳值；
  - 种群多样性：各维标准差、平均两两距离；
  - 可调参数是否卡在边界；
  - 如果优化器提供运行统计，也一并给出（numeric GA 提供子代与父代的平均距离）。
- 模型、预算、验证规则、单操作限制都与 B 组相同（`ab_v2_config.yaml`）。

## 设计

- **复用部分**：3 个 v2 任务 × 3 个种子只新跑 D 组。A、B、C 的结果复用 v2 网格；合并前用 mock 对照确认 A、C 的行为没有改变。
- **留出任务** `underflow_cost`（implementation 类，要最小化的成本 scorer 在部分区域下溢为很大的负值，没有替代实现）：3 个种子 × A/B/C/D。它是在 D 组写好之前设计的，纯 GA 预检查结果是：原版配置 0.004，只调目标 ≤ 0.006，正确清洗 0.994。在全部运行完成之前，不查看这个任务上的任何 LLM 结果。
- **主要指标**：
  - test split 上的固定外部指标，以及是否达到成功阈值（阈值在运行前已由 calibration 固定）；
  - 第一次提议是否选中已知的最佳目标；
  - 被接受的修改中，有多少属于最佳目标；
  - 调用次数、tokens、评估次数。
- **报告方式**：已见过的 3 个任务与留出任务**分开报告**。D 在前 3 个任务上的结果会偏乐观，因为改动正是针对这些任务上的失败设计的。留出任务的结果才是对"改进是否具有一般性"的检验。
- 每个任务只有 3 个种子，不做显著性检验。
