# v2 / v2b 结果：判断器（Judge）能否在 Planner 修不了的问题上起作用

- **性质**：真实 LLM（planner/analyzer/judge/scorer 匹配均为 `gpt-5-mini-2025-08-07`，拒答检测为 `gpt-4.1-nano`）+ **合成数值任务**。2026-10-20 在 Gautschi 登录节点 tmux 中运行。
- **代码版本**：A/B/C 为 81aef44；D 与留出任务为 9c11435。合并前用 mock 对照逐位确认，新代码下 A、C 的行为与旧代码完全相同。
- **配置**：`ab_v2_config.yaml` 与 `ab_v2b_config.yaml`，两者只有运行网格不同。预注册见 `../../PREREG_v2b.md`。
- **样本极小**（每个任务 3 个种子），不做显著性检验，不推断泛化。

## 设计

| 组 | 内容 |
|---|---|
| A | 原版 SAGA（Controller 关闭） |
| B | Controller + LLM Judge，提示词 v1：主要依据 Analyzer 的报告 |
| C | Controller + 随机选择干预目标（对照组，不调用 LLM），使用相同的验证门槛 |
| D | Controller + LLM Judge，提示词 v2：在 Analyzer 报告之外，提供 controller 直接计算的运行诊断，并要求先逐一评估五类目标 |

- 所有组以同一份预算为唯一停止条件：最多 50 次 LLM 调用、50 万 tokens、5000 次评估，墙钟时间上限 3000 秒。Analyzer 的提前停止对所有组都关闭。
- 每次提议最多一个操作。接受门槛：验证集上的增量 ≥ 0.02，且两个验证种子一致。
- **任务**：问题都由构造决定，Planner 改目标修不好（纯 GA 预检查已确认），并且已知最佳干预目标：
  - stagnant_search、noisy_search：优化器配置错误，最佳目标为 optimization_workflow。
  - overflow_scorer：scorer 溢出、且没有替代实现，最佳目标为 implementation。
  - underflow_cost（**留出任务**，在 D 写好之前设计）：scorer 下溢，最佳目标为 implementation。
- **D 的改动是在看到 B 在 stagnant_search 上的失败之后才设计的**，因此 D 在前三个任务上的结果偏乐观。

## Judge 的行为

| | B（v1） | C（随机） | D（v2 + 诊断） |
|---|---|---|---|
| 提议数 | 29 | 28 | 33 |
| 其中选中最佳目标 | 6（21%） | 5（18%） | **18（55%）** |
| 第一次提议就选中最佳目标 | 2/12 | 2/12 | **7/12** |
| 选择 optimization_workflow 的次数 | **0** | 8 | 14 |
| 被接受（其中属于最佳目标） | 4（3） | 3（3） | 7（5） |
| 因"一次多个操作"被判无效 | 5 | 0 | **9** |

- B（v1）一次也没有选过 optimization_workflow。它的理由能准确描述症状（多样性丧失、种群聚集），但把原因归到目标权重，与 Analyzer 报告中 "Strategic Recommendations (objective-level only)" 的说法一致。
- D 在提示词中被告知 Analyzer 的建议只限于目标层面，并拿到了诊断信息（例如 `mutation_sigma` 卡在下限、子代与父代的平均距离），于是转向了正确的干预目标。
- 所有被接受的修改都有正的验证增量。被接受但不属于最佳目标的，是在主问题修好之后附带的小幅目标调整（D 有 2 个），以及 B 在留出任务 s0 上的一次目标调整。

## 解读

1. **信息框定是主要障碍。** 同一个模型、同样的动作空间，只改变 Judge 看到的信息之后，第一次提议的目标准确率从 2/12 升到 7/12；在已见过的任务上，成功数从 1/9 升到 3/9。这支持"Judge 被 Analyzer 的目标层框架限制住了"这一假设。但这些任务正是 D 的设计依据，结果偏乐观。
2. **留出任务没有证实 D 具有一般性。** 在留出任务上 D 为 1/3，B 为 2/3，没有看到 D 的改进。这次的留出任务属于 implementation 类，问题会直接表现为"分数超出声明范围"，B 在这类问题上本来就能做得不错（overflow 1/3、underflow 2/3）。所以这个留出任务并没有检验 D 的主要改进点，即 workflow 类问题，这是设计上的不足。
3. **"验证 + 回滚"本身就有价值。** 随机目标（C）加上同样的门槛，在已见过的任务上平均测试指标（0.210）高于原版 A（0.066），而且没有任何有害修改被接受。在这组任务上，"安全的试错"已经优于原版。
4. **原版 SAGA 在这组任务上 0/12**，这是按构造预期的：问题都在 Planner 修不到的地方。
5. **D 的提示词有一个已知缺陷**：系统提示里写着可以改"1–3 个参数"，与"每次只允许一个操作"的限制不一致，导致 D 有 9 次提议被判无效，B 有 5 次。如果修正，D 的结果可能更好。为了保持预注册的一致性，这一轮没有中途修改。

## 运行中发现并修复的原版 SAGA 健壮性问题（对所有组相同）

- Analyzer 要求 `</reasoning>` 闭合标签，而 gpt-5-mini 经常省略（已在 v1 中修复）。
- Planner 重试时不把错误反馈给模型，导致同一个无效回答（weight=0）被反复提交（在 v2 第一次启动时修复，并从头重跑）。
- Analyzer 的拒答检测会出现误判。**本轮未修复**，并因此导致留出任务 A s0 运行失败。

## 下一步建议（未执行）

1. 统一提示词与 `max_ops_per_change` 的说法，然后重跑 D。
2. 增加 workflow 类的留出任务，以及更多种子，检验 D 的改进是否具有一般性。
3. 分离两种因素：做"v1 提示词 + 诊断"和"v2 提示词 + 无诊断"两组消融。
4. 换用更强的模型做 Judge，用来区分"信息不足"与"模型能力不足"。
5. 修复 Analyzer 拒答检测的误判（例如只把开头确实是拒答语句的回答判为拒答）。
