# v5 结果：验证器不完美时，框架还安全、还有用吗？（离线，不调用 LLM）

- **预注册**：`../../PREREG_v5.md`，含 2 次修订（都在看到 e2e 结果之前），修订原因写在文中。
- **代码**：f877d4d。**脚本**：`exps/meta_controller/validator_realism.py`。
- **规模**：3960 次端到端运行，另加 60 次真值测定，0 个报错。在登录节点上用 2 个进程，耗时 42 分钟。
- **原始数据**：`validator_realism/runs.jsonl.gz`、`gt_runs.jsonl`；汇总在 `summary.json` 和 `summary.md`。
- **稳健性检查**（修订 3，事后加做）：`validator_realism_noise_indep/`。只重跑 noisy 的全部设置和 A 组，共 1080 次，每格使用独立的噪声序列。

> **重要前提：本轮没有真实 LLM。**
> - Planner 和 Analyzer 都是 mock，目标集合固定不变。
> - "SIM"是**模拟判断器**：60% 概率提出正确修复，其余时候提出错误或"利用 bug"的修改。这是本研究的假设，不代表任何真实 LLM 的行为。
> - GA、Controller、门槛、scorer 都是真实代码。
> - 最终测试指标始终由**精确验证器的 test split** 计算，与门槛用的是哪种验证器无关。
> - 每个设置 60 格：6 个任务 × 2 种目标条件 × 5 个种子。不做显著性检验。

## 一句话结论

在这些合成任务和模拟判断器的假设下：

- **对测不准、略有偏差的验证器**，验证门槛基本稳健：仍有明显收益，单次判定很少接受明显有害的修改。噪声的主要代价是**不断接受无效修改、长期累积**。
- **只有代理指标、没有独立评价时**，scorer bug 这一类问题完全修不了：正确修复被接受 0/30。
- **10 倍验证成本**只在预算只够做 1–2 次判定时才是致命的。

## 实验设置（简述）

**门槛用的验证器（4 种）：**
- `oracle`：精确真值；
- `noisy`：每个候选的测量加 σ = 0.1 的高斯噪声；
- `biased`：真值模型的最优点偏移 0.1；
- `proxy`：直接用任务的初始代理 scorer 当验证器，包括其中埋的 bug。

**其他因素：**
- **验证成本**：1 倍或 10 倍；
- **门槛**：`v4`，或 `v4_floor`（v4 加上噪声下限：Δ ≤ 0.005 立即拒绝）；
- **预算**：5000 或 15000 次评估。

**组别：**
- **A**：无 Controller；
- **SIM**：模拟判断器；
- **RND**：随机目标判断器。

下表除特别说明外都是 `v4_floor` 门槛，它与 `v4` 的对比见第 6 点。完整表格（含 `v4`）见 `summary.md`。

## 主要发现

**1. 噪声验证器的风险不在"单次接受了明显有害的修改"，而在"不断接受看似无害的修改，长期累积成伤害"。**

- σ = 0.1 的测量噪声，落到判定用的 Δ 上，理论上是 σ ≈ 0.045，比接受门槛 0.02 还大。所以一个**完全没有效果**的修改，在第 1 阶段大约有 1/4 到 1/3 的概率被接受。
  - 本轮实测 Δ 噪声的标准差是 0.035。偏低的原因是噪声序列在各任务之间共享，见修订 3 和文末的稳健性检查。
- 在 noisy 条件下，被接受的修改中有 39/127 次精确 Δ < 0，但只有 1 次 ≤ −0.02。也就是说，按单次判定看几乎都"无害"。
- 但这些修改会与修复相互作用、长期累积。例如 frozen_mutation 上，`mutation_sigma = 0.3` 在修复之前没有作用（因为不发生变异）；修复之后，它会产生过大的变异。
- 结果：在主结果中，43 个接受过这类修改的格平均只有 0.379，只接受了修复的格是 0.806。整体收益比 oracle 少约 40%（+0.31 对 +0.52），但仍明显优于 A。相对 A 变差超过 0.05 的格只有 2/60。
- **稳健性检查改变了损失的幅度，但没有改变机制。** 每格用独立的噪声序列重跑后，Δ 噪声的标准差为 0.049，接近理论值：
  - 预算 15000、1 倍成本：noisy 的收益为 **+0.42**（oracle +0.52），损失约 20%，不是 40%。接受过"错误"修改的 37 格平均 0.498，只接受修复的 20 格是 0.845，机制仍然成立。
  - 预算 5000、1 倍成本：noisy 为 +0.38，oracle 为 +0.39，几乎没有损失。原因是只能做约 2 次判定，没有机会累积。
  - 主结果偏悲观，是因为同一串噪声同时作用在所有任务上，恰好不走运的那一段被放大了。
  - 结论：**噪声的代价随可做判定的次数增加而增加**。具体幅度对噪声的具体抽样很敏感，大约在 20%–40% 之间。
- **含义**：单次判定的门槛无法发现"慢性"伤害，用单次判定的对错来评估安全性会低估风险。真实场景中，验证测量的噪声必须明显小于接受阈值；否则就要估计噪声并相应提高阈值，或者在之后的轮次重新核查已接受的修改。这些办法本轮都没有测试。

**2. proxy 验证器（没有独立评价）：没有接受有害修改，但在最需要它的地方完全失效。**

- 在 3 个有 bug 的 scorer 任务上，正确修复被接受 **0/30**。原因是验证器和代理 scorer 共享同一个 bug：修复之后，"代理分"反而下降（例如 Δ = −1.6），于是修复被判为变差。拒绝时，精确 Δ ≥ +0.02 的有 129 次。
- 在优化器配置类任务上，proxy 与 oracle 表现相同，因为这些任务的代理 scorer 与真值方向一致。
- 预注册时预期 proxy 还会接受"利用 bug"的修改。**这一点没有观察到**：在修复之前，种群本来就已经停在 bug 区域，所以利用 bug 的修改不会再让代理分变高。
- **含义**：Meta-Controller 能修复 scorer bug，前提是有一个不共享该 bug 的独立评价。如果只有代理指标，这一类问题修不了。

**3. 本研究中的系统偏差（最优点偏移 0.1）几乎没有影响。**

- biased 与 oracle 的结果几乎相同（15000 / 1 倍：0.686 对 0.689）。
- 原因是这里的关键判定都是大效应（例如从 0 升到 0.8），偏差不会颠倒它们的方向。
- 注意：在 frozen_mutation 上，这个偏移其实相当大（偏差模型给真实最优点的评分只有 0.39），但仍然没有影响判定方向。
- **局限**：这里的偏差模型比较温和，没有测试"偏差会让效应符号反转"的情况，例如精细调参阶段。

**4. 验证成本是否致命，取决于预算够做几次判定。**

- **预算 5000**：
  - 1 倍成本时平均可做 2.0 次判定，10 倍成本时只能做 1.0 次（每次约 2500 次评估）。
  - 收益从 +0.39 降到 +0.13，成功数从 22 降到 7。
- **预算 15000**：
  - 1 倍成本可做 7.1 次判定，10 倍成本可做 4.3 次。
  - 收益几乎不变（+0.521 对 +0.517）。
- 10 倍成本下，验证本身占总预算的 25%（预算 5000）或约 37%（预算 15000）。
- 补充：目前每次验证都给种群中全部 32 个候选打分，但指标只用排名前 5 的候选。如果只测前 5 个，验证成本可降为原来的约 1/6。这一点尚未实现。

**5. 收益来自提议的质量，门槛本身不产生收益。**

- RND 在 1 倍成本时只有小幅收益（+0.04 ~ +0.15）。在 10 倍成本，或者验证器不完美时，收益基本消失，甚至为负（proxy、15000、10 倍成本：−0.022，60 格中有 7 格比 A 差超过 0.05）。
- SIM 的提议命中率为 60%，这是**假设**。真实 LLM 的命中率在 v3/v4 中大约是 50–64%（以"提出的修改属于最佳目标"计），而且很不稳定。

**6. 噪声下限（`v4_floor`）在验证器精确时有帮助，在噪声大时没有帮助。**

- 精确验证器下：
  - SIM oracle，预算 5000，1 倍成本：+0.357 → +0.390；
  - SIM oracle，预算 15000，10 倍成本：+0.476 → +0.517；
  - RND oracle，预算 15000，10 倍成本：+0.015 → +0.042。
  - 原因是 v4 会把 Δ 极小的无效修改延长测试，耗尽预算；`v4_floor` 避免了这一点。
- noisy 下：+0.337 → +0.329（5000），+0.311 → +0.307（15000），基本没有变化。因为在噪声大时，Δ 往往远离 0，噪声下限很少起作用。

**7. 仍然存在"做了反而比不做差"的格子。**

- 预算 5000、SIM oracle 时，比 A 差超过 0.05 的格子是 1 倍成本 4/60、10 倍成本 6/60，**全部在 stagnant_search 上**。
- 原因：在这个任务上，A 不做干预，靠更多的主循环轮数也能慢慢改进；而 Controller 把预算花在了验证上，导致主循环轮数变少。
- 预算 15000 时，SIM 的 oracle 和 biased 条件下这类格子为 0/60。

## 与预注册预期的对照

| 预期 | 结果 |
|---|---|
| noisy / biased：有害修改的采纳率略升、收益下降，但仍优于 A | noisy：**成立，但机制与预期不同**。单次判定的有害接受很少，收益下降来自"看似无害"修改的长期累积。预算 15000 时收益下降约 20%–40%（取决于噪声抽样），预算 5000 时几乎不降，始终优于 A。biased：**不成立**，几乎没有影响（偏差模型较温和） |
| proxy：在有 bug 的任务上拒绝正确修复、接受利用 bug 的修改；在优化器配置任务上与 oracle 接近 | 拒绝修复：**成立**（0/30）。与 oracle 接近：**成立**。接受利用 bug 的修改：**没有观察到**（原因见发现 2） |
| 10 倍成本：干预次数大幅减少、收益明显下降，甚至可能低于 A | 预算 5000：**成立**，收益降到约 1/3，但 SIM 仍高于 A。预算 15000：几乎不受影响。RND：在 10 倍成本下接近 A 或低于 A |

## 局限

1. **判断器是模拟的。** 结论只在"60% 命中率、错误修改从固定菜单中选"这一假设下成立。
2. **Planner 是 mock，目标固定。** 真实 Planner 每轮都会改目标，会与已接受的修改相互作用（v4 已经观察到这一点）。
3. **任务和修改菜单是我们自己设计的。** 其中的 bug 与修复是专门配对的，存在循环论证的风险。
4. **精确 Δ 只看最后一个阶段的一轮效果。** 正如发现 1 所示，它看不到长期伤害。
5. **噪声是独立同分布的高斯噪声；偏差是最优点的平移。** 真实实验中的误差结构可能更复杂。主结果中噪声序列在各任务之间共享（修订 3），稳健性检查表明，噪声代价的幅度对抽样很敏感。
6. 每个设置 60 格，没有做显著性检验。

## 建议的下一步（均未执行）

1. **噪声感知门槛**：对同一个种群重复测量，估计 Δ 的标准差，要求 Δ 大于 2σ；或者按噪声来设定 `min_improvement`。可以先离线校准。
2. **已接受修改的"试用期"**：在之后几轮里重新核查已接受的修改，变差就回滚。这针对的是发现 1 中的累积伤害。
3. **只测排名前 k 的候选**：把验证成本降到原来的约 1/6，缓解发现 4 中的成本问题。
4. **真实 LLM + noisy 验证器的小规模端到端运行**：检验真实判断器在噪声下的表现。这一步需要 API 费用，跑之前会先和你确认。
